# Mensagem para enviar ao chat com acesso ao GitHub, Vercel e Supabase

> Tenho um ZIP com o código revisado do Mapa de Reparos. Extraia os arquivos e substitua o conteúdo do repositório `Reparos05-Monteiro/Process` na branch `main`, respeitando as pastas. Remova os antigos `app.js`, `styles.css` e `hub.css` da raiz. Não faça commit do ZIP, da pasta `node_modules`, de `dist`, de arquivos `.env` ou de chaves secretas.
>
> Antes da publicação, use o projeto Supabase escolhido, execute `supabase/schema.sql` no SQL Editor, crie/identifique **minha** conta no Supabase Authentication e me peça para identificar o e-mail se houver dúvida. Vincule o UUID correto em `public.repair_members` com `role = 'admin'` conforme o README. Desative cadastro público; não invente credenciais e não insira dados fictícios. Confirme que `public.repair_cases` está vazia. Revise políticas RLS e grants; visitantes não podem ler casos nem modificar configurações, editores podem gerir casos, só o administrador pode editar etapas e preferências.
>
> Use o projeto `process` já existente na Vercel se ele existir. Conecte `Reparos05-Monteiro/Process` branch `main`, configure Vite com `npm ci`, `npm run build`, saída `dist` e adicione `VITE_SUPABASE_URL` e `VITE_SUPABASE_PUBLISHABLE_KEY` como variáveis de ambiente. Use somente a chave pública publishable no frontend. Rode `npm test` e `npm run build`, publique e confira a tela inicial, login, mapa vazio, criação/edição de caso, mudança de etapa, edição/reordenação de etapas e bloqueio de permissões para editor/visitante. Envie o link publicado, o SHA do commit e diga quais testes passaram. Não considere a entrega finalizada se faltar acesso real ao Supabase ou se o deploy mostrar apenas a tela de configuração pendente.

O README do ZIP contém as etapas detalhadas, SQL de vinculação do administrador e a matriz de permissões. Compartilhe o ZIP inteiro com esse chat e mantenha a senha da conta somente no fluxo seguro de autenticação.
